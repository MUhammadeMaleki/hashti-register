# هشتی

پیاده‌سازی نسخه اول بر مبنای [PRD](Hashti_PRD_v1.3.md) و [طراحی فنی](tech_design.md).
Backend با FastAPI و SQLAlchemy 2، Frontend با Next.js App Router و TypeScript و دیتابیس PostgreSQL است؛ Docker استفاده نمی‌شود.

الگوهای استقرار Linux، بکاپ و بازیابی در [راهنمای استقرار](deploy/README.md) هستند؛ جایگزین آزمون روی سرور واقعی نیستند.

## پیش‌نیازها

Python 3.11 یا جدیدتر، Node.js نسخه 20.9 یا جدیدتر، npm و PostgreSQL 17. دستورهای زیر از ریشه پروژه و در PowerShell اجرا می‌شوند.

## دیتابیس محلی

اگر دیتابیس اختصاصی پروژه ندارید:

```powershell
.\scripts\local-postgres.ps1 start
```

این دستور با باینری PostgreSQL نصب‌شده، یک cluster اختصاصی در `.local/postgres-dev` روی `127.0.0.1:55432` می‌سازد؛ به سرویس PostgreSQL فعلی دست نمی‌زند. دیتابیس‌های `hashti_dev` و `hashti_test` با نقش محدود `hashti_app` ساخته می‌شوند. رمز تصادفی در فایل نادیده‌گرفته‌شده `backend/.env` قرار می‌گیرد و چاپ نمی‌شود. این ابزار مخصوص توسعه محلی است، نه استقرار سرور. مسیر باینری با `-PostgresBin` قابل تغییر است. در اجرای مجدد، داده‌ها حفظ و همان cluster راه‌اندازی می‌شود.

```powershell
.\scripts\local-postgres.ps1 status
.\scripts\local-postgres.ps1 stop
```

در صورت استفاده از PostgreSQL خودتان، `backend/.env.example` را به `backend/.env` کپی کنید و URL دیتابیس توسعه و یک دیتابیس تست جداگانه با نام ختم‌شونده به `_test` را وارد کنید. هیچ رمز واقعی در فایل example یا Git قرار ندهید. از دیتابیس موجودِ غیرمرتبط یا production برای تست استفاده نکنید.

احراز هویت به `HASHTI_AUTH_SECRET` تصادفی و `HASHTI_PUBLIC_ORIGIN` دقیق نیاز دارد. راه‌انداز PostgreSQL جدید secret را خودکار در `.env` می‌نویسد؛ برای `.env` موجود یک‌بار `.\scripts\ensure-auth-secret.ps1` را اجرا کنید. مقدار پیش‌فرض origin برای توسعه `http://127.0.0.1:3000` است؛ در محیط توسعه `localhost` و `127.0.0.1` با همان scheme و port هم‌ارز هستند. در استقرار واقعی origin باید HTTPS باشد.

## نصب و اجرای Backend

```powershell
python -m venv backend/.venv
backend/.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
Set-Location backend
.venv/Scripts/python.exe -m alembic upgrade head
.venv/Scripts/python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

`http://127.0.0.1:8000/api/health` زنده‌بودن برنامه و `/api/health/ready` اتصال واقعی دیتابیس را نشان می‌دهد. readiness در زمان قطع دیتابیس با `503` و بدون اطلاعات اتصال پاسخ می‌دهد. مستند API در `/docs` در دسترس است.

API احراز هویت در `/api/auth` فعال است: ساخت حساب مستقل مهمان، ورود مدیر/مهمان، refresh چرخشی، خروج، مشاهده نشست و تغییر رمز. صدور رمز موقت در `/api/admin/guests/{id}/temp-password` برای مدیر یا دبیر فعال است. نشست‌ها در cookieهای `HttpOnly` نگهداری می‌شوند؛ درخواست‌های تغییردهنده با نشست باید header `X-CSRF-Token` برابر cookie خواندنی `hashti_csrf` و `Origin` مجاز بفرستند. رمز موقت پس از ۲۴ ساعت یا یک ورود موفق دیگر قابل ورود نیست و مهمان باید رمز شخصی جدید تعیین کند. در محیط توسعه cookieها روی HTTP محلی کار می‌کنند؛ خارج از توسعه `Secure` هستند.

مدیریت دبیران در `/api/admin/users` و تنظیمات در `/api/admin/settings` فقط برای مدیر هشتی فعال است. حذف سخت دبیر وجود ندارد؛ `PATCH /api/admin/users/{id}` با `is_active: false` حساب را غیرفعال و نشست‌هایش را باطل می‌کند، ولی سابقه و انتساب رویداد باقی می‌ماند. کنترل انتساب در endpointهای رویداد و پورتال مهمان فعال است.

مدیریت رویداد و مکان در `/api/admin/events` و `/api/admin/locations` فعال است. دبیر ایجادکننده خودکار به رویداد منتسب می‌شود و تغییر رویداد به دبیران همان رویداد یا مدیر هشتی محدود است. شمارهٔ پیشنهادی `/api/admin/events/next-number` رزرو قطعی نیست؛ تکرار شماره هنگام ذخیره با `409` رد می‌شود. ویرایش مکان ذخیره‌شده در همهٔ رویدادهای متصل دیده می‌شود؛ مکان وابسته حذف نمی‌شود. لغو رویداد و ثبت‌نام، هزینه‌های فعال را لغو و تسویه‌ها را اتمیک برمی‌گرداند. فعال‌سازی مجدد رویداد، ثبت‌نام‌های قبلی یا سوابق مالی را خودکار بازنمی‌گرداند.

داشبورد `/panel` و گزارش‌های `/panel/reports` برای همهٔ دبیران فعال قابل مشاهده‌اند: جمع مالی رویداد از هزینه‌های لغونشده و تسویه/برگشت دفتر محاسبه می‌شود؛ فیلترهای مهمان و نمودارها در بازهٔ انتخابی اعمال می‌شوند. گزارش تطبیق کیف پول و دفتر فقط برای مدیر هشتی است و هیچ مانده‌ای را خودکار اصلاح نمی‌کند. جدول‌های مهمان‌ها، وضعیت مالی و بدهکاران رویداد از همان صفحه با فیلترهای اعمال‌شده به Excel صادر می‌شوند؛ خروجی همهٔ ردیف‌های منطبق را مستقل از صفحه‌بندی نمایش دربر می‌گیرد.

ورود اولیه مخاطبان از `/panel/import` انجام می‌شود: فایل نمونه را بگیرید، ستون موبایل را متنی نگه دارید، فایل XLSX را پیش‌نمایش کنید و فقط ردیف‌های معتبر را تأیید کنید. محدودیت هر فایل ۳ مگابایت و ۵۰۰۰ ردیف است. پیش‌نمایش تا ۳۰ دقیقه معتبر است و تأیید دوبارهٔ همان فایل پروفایل تکراری نمی‌سازد. خطاها با شمارهٔ ردیف Excel گزارش می‌شوند؛ مخاطبان واردشده کیف پول صفر دارند و حساب ورود یا ثبت‌نام رویداد برایشان ساخته نمی‌شود.

ورود آرشیو رویدادها در `/panel/events/import` فقط برای مدیر هشتی است. فایل نمونهٔ Excel، پیش‌نمایش و تأیید دارد؛ تنها شمارهٔ یکتای رویداد الزامی است و عنوان خالی با «هشتی + شماره» پر می‌شود. تاریخ متنی باید میلادی و به‌شکل `YYYY-MM-DD` باشد. ردیف‌های تکراری یا نامعتبر با شمارهٔ ردیف گزارش می‌شوند و مانع ورود ردیف‌های معتبر نیستند. رویداد بدون پوستر، مکان یا تاریخ هم وارد آرشیو می‌شود؛ هیچ مهمان یا سابقهٔ حضور/غیبت برای آن ساخته نمی‌شود.

پس از Migration، مدیر هشتی اولیه را تعاملی بسازید؛ رمز حداقل ۱۲ کاراکتری در ترمینال نمایش داده نمی‌شود و فقط هش Argon2id آن ذخیره می‌شود:

```powershell
Set-Location backend
.venv/Scripts/python.exe -m app.seed --admin-username admin --admin-name "مدیر هشتی"
```

افزودن `--demo` یک رویداد بسته، مکان، برچسب و مهمان نمونه با کیف پول صفر می‌سازد و فقط در محیط توسعه مجاز است. اجرای دوباره seed دادهٔ نمونه را تکرار نمی‌کند. این دستور روی دیتابیس انتخاب‌شده در `backend/.env` اثر می‌گذارد؛ پیش از اجرا URL آن را بررسی کنید.

## نصب و اجرای Frontend

در پنجره دوم، از ریشه پروژه:

```powershell
Set-Location frontend
npm ci
npm run dev
```

صفحه توسعه در `http://127.0.0.1:3000` باز می‌شود. درخواست‌های `/api/*` به Backend روی پورت 8000 بازنویسی می‌شوند؛ مرورگر از همان origin استفاده می‌کند. در صورت نیاز `frontend/.env.example` را به `.env.local` کپی و `BACKEND_ORIGIN` را تنظیم کنید. برای تغییر این مقدار در production باید Frontend را دوباره build کنید.

رابط فارسی/RTL در `/login` برای ورود دبیر و مهمان و ساخت حساب مهمان آماده است. کاربر پس از ورود به `/panel` یا `/account` هدایت می‌شود؛ مهمان دارای رمز موقت ابتدا در `/change-password` رمز شخصی تعیین می‌کند. نشست در cookieهای Backend باقی می‌ماند و در `localStorage` ذخیره نمی‌شود. کلاینت درخواست‌های تغییردهنده را با CSRF می‌فرستد و نشست منقضی را یک‌بار refresh می‌کند. فهرست حساب‌های مدیریتی در `/panel/users` فقط برای مدیر هشتی از API خوانده می‌شود. پورتال مهمان، پروفایل، ثبت‌نام‌های فعال، کیف پول، گردش کامل، بدهی هر رویداد، رسیدهای مستقل و رویدادی و تسویه با کیف پول خود را نشان می‌دهد. ثبت‌نام، کیف پول، رسیدها و لغو/بازگردانی رویداد و ثبت‌نام در پنل فعال‌اند.

فهرست و فرم رویدادها در `/panel/events` و بانک مکان‌ها در `/panel/locations` آماده‌اند. تاریخ در فرم به شمسی وارد و به تاریخ استاندارد API تبدیل می‌شود؛ تاریخ گذشته نیز مجاز است.

پوستر هنگام ساخت رویداد قابل انتخاب است و پس از ایجاد آن بارگذاری می‌شود؛ در ویرایش رویداد دکمهٔ جداگانهٔ «بارگذاری پوستر» دارد. دبیر می‌تواند از جدول مهمان‌های رویداد تسویهٔ بدهی را تا سقف موجودی کیف پول انجام دهد. مدیر هشتی شماره کارت مجموعه و سقف عمومی بدهی را در `/panel/settings` تنظیم می‌کند. در صفحات عمومی، مهمانِ واردشده به جای دکمهٔ ورود، میانبرهای پروفایل و کیف پول را می‌بیند.

## بررسی و تست

```powershell
Set-Location backend
.venv/Scripts/python.exe -m ruff check .
.venv/Scripts/python.exe -m pytest -q
Set-Location ../frontend
npm run typecheck
npm test
npm run build
npm run start
```

پس از اجرای هر دو برنامه، از ریشه پروژه `node scripts/smoke.mjs` را اجرا کنید تا پاسخ صفحه فارسی/RTL، سلامت API و اتصال PostgreSQL از طریق proxy واقعی Frontend بررسی شود.

تست دیتابیس روی PostgreSQL واقعی اجرا می‌شود و در صورت نبود تنظیمات تست شکست می‌خورد؛ با SQLite یا mock جایگزین نمی‌شود. اجرای تست‌ها ابتدا `alembic upgrade head` را فقط روی دیتابیس تست اجرا می‌کند. Migration `0001_bootstrap` زنجیره را راه‌اندازی می‌کند و Migration `b30ce05cd3ac_domain_schema` هجده جدول دامنه و قیود اصلی را می‌سازد. تست ساخت از اسکیمای خالی در یک تراکنش جدا اجرا و برگردانده می‌شود.

وابستگی‌های Python در `requirements.in` تعریف و نسخه‌های نصب‌شده در `requirements.txt` قفل می‌شوند. وابستگی‌های Frontend در `package-lock.json` قفل‌اند. فایل‌های `.env`، دیتابیس محلی، virtualenv و خروجی build در `.gitignore` هستند.

برنامه و وضعیت تسک‌ها در `implementation_plan.json` و معیارهای پذیرش در `acceptance_checklist.json` نگهداری می‌شوند.
